### HTTP 入站的背景壓縮

官方 Codex 在 `codex-rs/core/src/compact_remote_v2.rs` 的背景分支建立獨立的 `ResponsesHttpExecutor`，複用路由 token；前景分支則使用回合的 `ModelClientSession`。CPR 辨識 turn metadata 的 `request_kind: compaction` 或輸入的 `compaction_trigger`，同時考慮顯式 WS 偏好、入站 WS 連線和預熱。歷史中的 `compaction` 結果不會讓下一個普通回合改走 HTTP。

核對 vm2api `a6455dcd603757fa4508d97f866fa1fe98b864d6` 的 `src/lib/protocol/responses-ws.mjs`、`src/lib/protocol/handle-codex.mjs` 與 `src/lib/transport/codex-kernel-env.mjs`。入口知道 `req.inboundTransport`，並對 WS 請求附上 `options.ws_replay`；送給核心的 `upstream_transport` 取自路由設定。目前 HTTP 入站即使帶有壓縮標記，在 `prefer_websocket` 下仍可能先走 WS。這是原始碼比對，這輪沒有執行背景壓縮流量測試。

Kin 的 [請求選項](../../crates/contract/src/envelope.rs) 已支援逐次指定 `http`。[傳輸選擇](../../crates/upstream/src/lib.rs) 服從該選項，[HTTP 標頭](../../crates/upstream/src/headers.rs) 可攜帶 `x-codex-turn-state`。既有 [HTTP 整合案例](../../crates/api/tests/responses_http.rs) 涵蓋強制 HTTP 的完整快照及原生 WS 增量限制。若要對齊 CPR，落點在 vm2api 組裝請求選項時，僅對符合條件的 HTTP 入站壓縮指定 `http`，並驗證 WS 入站、預熱及一般回合。本輪 Kin 無須修改 ABI 或傳輸程式。
